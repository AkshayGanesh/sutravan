<objective>
Notify admins on every new customization ("skin care guide") questionnaire submission across TWO surfaces: (1) an in-app unread badge in the admin portal driven by a new `status` column on `customization_submissions`, and (2) one best-effort email per submission sent server-side from the existing `verify-and-submit` Edge Function.

Purpose: The owner currently has no signal that a customer submitted the questionnaire — they must remember to check the inbox. This adds a passive badge and an active push email.
Output:
- Migration `0009_submissions_status.sql` — `status` column (default `'new'`) + admin-only UPDATE RLS policy.
- Frontend: unread-count hook + mark-read mutation + badge on the Submissions nav link + `status` highlight in the inbox + mark-read-on-open.
- Edge Function: best-effort admin email after the insert succeeds.
- TWO blocking-human steps surfaced together at the end (live `supabase db push` + Resend account/secrets/`functions deploy`).
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| customer browser → customization_submissions (PostgREST) | Untrusted customer could attempt to mutate `status` directly |
| customer browser → verify-and-submit Edge Function | Untrusted body crosses into server-side insert + email |
| Edge Function → Resend HTTP API | Server-side secret crosses to a third-party email provider |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-CO6-01 | Elevation of Privilege | customization_submissions UPDATE | mitigate | New `customization_submissions_admin_update` policy gates UPDATE on `private.is_admin()` (using + with check); a non-admin customer cannot change `status`. SELECT/INSERT policies untouched — no read/insert widening. |
| T-CO6-02 | Information Disclosure | RESEND_API_KEY / ADMIN_NOTIFY_EMAIL | mitigate | Secrets read only via `Deno.env.get` in the Edge Function (T-05-09 pattern, same as TURNSTILE_SECRET_KEY); never `VITE_`/bundled. Grep gate scoped to `client/` enforces no client-side reference. |
| T-CO6-03 | Denial of Service | submission insert path | mitigate | Email send is best-effort try/catch; a Resend outage/error logs server-side and the function still returns `{ok:true}` — the customer's submission never fails because email failed. |
| T-CO6-04 | Information Disclosure | admin notification email body | accept | Email contains submitter name/email/skin_type (the same data the owner already sees in the inbox) sent only to the owner-controlled ADMIN_NOTIFY_EMAIL. Low risk for a small no-payments brand; no new PII surface beyond the existing inbox. |
| T-CO6-SC | Tampering | npm/deno installs | accept | No new npm packages added (frontend reuses existing TanStack Query + sidebar kit). The Edge Function calls the Resend REST API over `fetch` — no new dependency to vet (Deno imports unchanged). |
</threat_model>
