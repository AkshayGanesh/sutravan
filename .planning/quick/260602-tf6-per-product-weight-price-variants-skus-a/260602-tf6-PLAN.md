<objective>
Add per-product weight/price variants (SKUs). A product may sell in multiple weights (e.g. 70gm, 200gm),
each with its own price. The public product detail shows the options with prices and lets the customer
switch (the shown price updates); Shop/Home cards show "From ₹{lowest variant price}". The admin manages
variants per product on the product editing page. Catalog display + admin management only — NO
cart/checkout (e-commerce is a later milestone).

Purpose: Lets the owner sell the same product in multiple sizes/prices without code changes or redeploys —
managed entirely through the admin portal (the milestone's core value).

Output:
- New migration 0011 creating `public.product_variants` (a REAL relational table WITH RLS policies).
- `variants` wired end-to-end: a small pure variants.ts lib (mapper + price derivations), catalog.ts
  public read (nested select), admin.ts write (a diff-based persistence path), a repeatable variant-row
  editor on ProductForm, a weight-option selector on ProductDetail, and "From ₹{lowest}" on ProductCard.

LOCKED DECISIONS (from 260602-tf6-CONTEXT.md — DO NOT revisit):

1. SEPARATE `product_variants` TABLE (not a JSON column). Columns: `id uuid pk default gen_random_uuid()`,
   `product_id uuid not null references public.products(id) on delete cascade`, `label text not null`
   (e.g. "70gm"), `price numeric(10,2)` (SAME type as products.price), `sort_order int not null default 0`,
   `created_at`/`updated_at timestamptz default now()`. Index on `product_id`. RLS enabled; PUBLIC SELECT +
   ADMIN-ONLY write via `private.is_admin()` — mirror the products policies (0002).

2. VARIANTS ARE OPTIONAL; they DRIVE pricing only WHEN PRESENT. 0 variants -> the product renders EXACTLY
   as today (single `products.price`, incl. null = "Price on request"). >=1 variant -> variants become the
   pricing source and `products.price` is IGNORED for display. Fully backwards-compatible: NO data
   migration of the 28 existing products (they have 0 variants and stay unchanged).

3. SHOP CARD: "From ₹{lowest variant price}" when variants exist; the unchanged single price otherwise.
   REUSE the existing `formatPrice` helper (client/src/lib/format.ts) — do NOT invent a parallel
   formatter. The "From " prefix is prepended to formatPrice's output.

CRITICAL — THIS TABLE LEGITIMATELY HAS POLICIES. Unlike the recent boolean-flag migrations (0008/0010,
which were display columns on an existing table and therefore touched NO policy), product_variants is a
NEW relational table that MUST enable RLS and create policies. DO NOT add a no-policy grep gate to the
migration verify; the migration MUST contain `create policy`.

PUBLIC-READ RLS SCOPING (CONTEXT decision — gate to is_active products): make the public SELECT policy
return variants ONLY for products that are publicly readable, mirroring the CR-01 intent (0005 tightened
products_public_read to `using (is_active = true)`). Use a subquery:
`using (exists (select 1 from public.products p where p.id = product_variants.product_id and p.is_active))`.
This keeps draft products' variants off the public read path, consistent with their parent. TRADEOFF: this
adds a per-row products subquery on variant SELECT — negligible for this ~28-product catalog and the
correct posture. (A plain `using (true)` public-read is the documented acceptable fallback if the subquery
proves awkward, but the subquery is preferred and expected here.)

UUID vs SLUG — READ CAREFULLY. The public Product's `id` field is the product SLUG (catalog.ts toProduct
sets `id: row.slug`), and the admin write path keys products off `slug` (useUpsertProduct updates
`.eq('slug', ...)`; insertProductWithUniqueSlug returns a slug). But `product_variants.product_id` is the
products UUID (`products.id`). So the variant write path MUST resolve the product's UUID by slug after the
product upsert before inserting/updating variants. catalog.ts's nested select rides the embedded relation,
so the public read does not need the UUID surfaced.
