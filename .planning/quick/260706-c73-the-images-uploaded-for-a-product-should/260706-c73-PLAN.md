<objective>
Make the uploaded product-image thumbnails in the admin ProductForm Photos section
drag-reorderable. Today the tiles render in fixed array order with no way to change it.

Purpose: The first image in `products.images` is the primary/card image on the public
shop; the owner needs to control which photo leads and the overall sequence without
deleting and re-uploading.

Output: A single edited client component — `ImageDropzone.tsx` — where committed
thumbnails can be dragged into a new order via a grip handle, emitting the new order
through the existing `onChange`. No backend, schema, or migration work: persistence
already rides array order (`fromProductForm` writes `images: v.imagePaths`, the public
shop reads that array in order). No new npm dependency: `framer-motion` (^12.23.24) is
already installed and already used for drag-reorder in `RepeatableRows.tsx`.
</objective>

  <name>Task 1: Make committed thumbnails drag-reorderable via framer-motion Reorder</name>
  <files>client/src/components/admin/ImageDropzone.tsx</files>
  <action>
Add drag-to-reorder to the committed image thumbnails, mirroring the proven
handle-only pattern in `RepeatableRows.tsx` (read it first).

Imports: add `Reorder, useDragControls` from "framer-motion" and `GripVertical` from
"lucide-react" (`X` is already imported).

Restructure the thumbnails block (currently the `<ul className="flex flex-wrap gap-3">`
that maps `value` then `pending`):

- Wrap the committed `value.map(...)` tiles in a `Reorder.Group` rendered as the list
  element: `as="ul"`, keep `className="flex flex-wrap gap-3"`, `axis="x"`,
  `values={value}`, and wire `onReorder={onChange}` DIRECTLY. This works with no id
  bookkeeping because Storage paths are unique and stable (unlike RepeatableRows, whose
  rows can be empty/duplicate) and `onChange` already accepts `string[]` — the reordered
  paths array is exactly what onChange wants. Note: tiles wrap (2D), so drag reorder is
  functional but animation across a wrap boundary may be imperfect — acceptable; do not
  add a new dependency to "improve" it.
- Extract each committed thumbnail into a small child component (e.g.
  `ReorderableThumb`) so `useDragControls()` is called ONCE per item at the top level,
  NEVER inside a `.map` callback — exactly as `RepeatableRow` is extracted in
  RepeatableRows.tsx. The child renders `Reorder.Item value={path} as="li"
  dragListener={false} dragControls={controls} className="relative"` and contains:
  (a) the existing `<img src={thumbUrl(path)} .../>` unchanged;
  (b) the existing X remove `<button>` unchanged (still calls `requestRemove(path)`);
  (c) a NEW small GripVertical drag handle overlaid on the tile (e.g. bottom-left
  corner, a small rounded chip like the X uses at top-right), with
  `className="... cursor-grab touch-none"`, an `aria-label` such as
  `` `Reorder photo ${index + 1}` ``, and `onPointerDown={(e) => controls.start(e)}`.
  Handle-only drag (`dragListener={false}`) is what guarantees the X remove click and
  mobile page-scroll are never hijacked by the drag gesture — the same rationale as
  RepeatableRows.
- Keep the pending/uploading tiles NON-reorderable and rendered AFTER the committed
  items so the single flex-wrap gap-3 row looks identical to today. `values={value}`
  lists only committed paths, so pending tiles never participate in reorder. Render them
  as static (plain `<li>`) children after the Reorder.Items inside the same group, or as
  an adjacent sibling list — whichever keeps framer happy and the visual identical.
- Keep the outer guard `(value.length > 0 || pending.length > 0)` wrapping the whole
  block.

Do NOT touch: `handleOneFile`/`handleFiles` upload pipeline, the `savedRef` snapshot,
`requestRemove`/`confirmRemove`/`removePath`, the `ConfirmDialog`, `thumbUrl`, or the
drop zone. `savedRef` is a Set keyed by path, and reordering is a pure permutation (no
add/remove), so it stays valid with zero changes. Upload's `onChange([...value, path])`
append is likewise unaffected.
  </action>

  </done>
