<objective>
Ship cross-device pincode persistence (DLVR-10) as a complete vertical slice by extending
the EXISTING `DeliveryProvider` in place — no second provider (D-09), public context shape
`{ pincode, setPincode }` unchanged. Two additions: (1) a login-merge read effect that
reconciles `profiles.default_pincode` against localStorage on login (D-01 profile wins;
D-02 adopt an anonymous local choice into an empty profile), and (2) a best-effort
write-through inside `setPincode` so a logged-in customer's every change saves to their
profile (D-03). Profile I/O is silent-degrade (D-08): a failed read/write never toasts and
never blocks the local/session pincode. An anonymous visitor is untouched — localStorage
only (D-04).

The merge decision (`profile-if-set, else adopt-local, else noop`) is extracted to a pure,
unit-tested helper so the D-01/D-02 logic is provable without a React/Supabase harness.

Purpose: SC4 (profile save + cross-device restore + login merge) and the logged-in half of
SC3, with zero changes to the Phase 7 estimator or the pill.
Output: `loginMerge.ts` (+ test) and an extended `DeliveryProvider.tsx`.
</objective>

## Phase Goal (MVP user story)

Derived faithfully from the ROADMAP Phase 8 goal + the 4 success criteria (same story as
Plan 01; this plan delivers the account-sync slice):

**As a** Sutravan shopper, **I want to** set or change my delivery pincode from a navbar
widget on any page — with the choice remembered site-wide (and tied to my account when I'm
logged in), **so that** I never re-enter it between pages or devices and every delivery
estimate reflects where I actually am.

**This plan delivers the profile-persistence slice:** a logged-in customer's pincode saves
to their account and restores on a fresh login from another device/session; a first-time
customer who typed a pincode while anonymous keeps it (adopted into their new profile).

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-08-02 | Elevation of Privilege / Tampering | `profiles.default_pincode` client write | mitigate | Update is `.eq("id", userId)` under the caller's JWT; the `profiles` RLS update policy scopes writes to `auth.uid() = id`, and the Phase-3 `enforce_profile_role_lock` BEFORE UPDATE trigger (migration 0004) blocks any `role` change regardless of payload. The write payload is minimal `{ default_pincode }` only — the negative grep (`! .update({...role...})`) enforces no role/extra column leaks. No new endpoint, no service-role. |
| T-08-03 | Information Disclosure | login-merge read of `profiles.default_pincode` | mitigate | `select("default_pincode").eq("id", userId).single()` returns only the caller's own row under owner-scoped RLS (same posture as AuthProvider's role read). No other user's pincode is reachable. |
| T-08-04 | Denial of Service | write-through on every `setPincode` (no debounce, D-03) | accept | Pincode changes are infrequent and deliberate; the write is best-effort and silent (D-08). No captcha needed — this is a location setter, not the rate-limited estimator (D-05). Residual abuse risk is negligible for a small no-payments brand. |
| T-08-SC | Tampering | npm/pip/cargo installs | accept | No new dependencies added this plan — the provider reuses existing `@/lib/supabase`, `@/auth/useAuth`, and React. No install task. |
</threat_model>
