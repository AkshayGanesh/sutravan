<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → Edge Function (`verify-and-submit`) | Untrusted submission body + Turnstile token cross here; the function holds the only server-side secret. |
| Edge Function → PostgREST (`customization_submissions` INSERT) | Insert crosses under the caller's JWT; RLS WITH CHECK (0007) is the real ownership gate. |
| browser → PostgREST direct (`customization_submissions` INSERT) | The function can be bypassed; 0007 still scopes `user_id`, but Turnstile is skippable on this path (Open Question 1). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-05 | Tampering / Elevation | `customization_submissions` INSERT (forge another user's `user_id`) | mitigate | 0007 WITH CHECK: authenticated → `user_id = (select auth.uid())`, anon → `user_id is null`. Insert runs under the caller's JWT (not service role) so the check actually fires. Verified live in Task 3.6 (forged-uid rejected). |

| T-05-07 | Spoofing / DoS (spam) | Turnstile verification | mitigate | Token verified server-side via `siteverify` with the secret held only in the function env; secret never `VITE_`/bundled. Invalid token → 400, no insert (Task 3.7). |

No `[ASSUMED]`/`[SUS]` package install in this plan, so no package-legitimacy checkpoint is triggered. |
