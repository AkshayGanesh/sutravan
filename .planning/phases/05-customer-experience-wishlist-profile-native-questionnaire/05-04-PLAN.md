<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `profiles` UPDATE | Untrusted name update crosses here; RLS + role-lock trigger gate it. |
| browser → GoTrue `updateUser` (email/password) | Credential change handled by Supabase Auth, not app code. |
| browser → `customization_submissions` SELECT (own history) | RLS admin-or-owner SELECT scopes rows to the caller. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-15 | Information Disclosure | `/profile` submission history (read another user's rows) | mitigate | `useMySubmissions` rides the existing `customization_submissions_admin_or_owner_read` RLS — a non-admin caller only ever receives their own rows. No service-role path. Verified live (Task 3.5). |
| T-05-16 | Elevation | `profiles` self-update (escalate role via name form) | mitigate | The name form only sends `{ name }`; the Phase-3 `enforce_profile_role_lock` BEFORE UPDATE trigger blocks any `role` change regardless of client payload (0004). The form has no role field. |
| T-05-17 | Spoofing (account takeover via email change) | email change flow | mitigate | "Secure email change" ON → GoTrue double-confirmation; the UI shows a pending notice and the address does not change until the link is clicked (D-14/Pitfall 5). No app-side bypass. |
| T-05-18 | (open redirect) | logged-out `/profile` → AuthGuard `?next=` | mitigate | AuthGuard (Plan 01) reuses `safeReturnTo` — `?next=/profile` is an internal leading-slash path; scheme/`//` rejected. |
| T-05-19 | Information Disclosure | password field handling | accept | Password is sent directly to GoTrue over TLS via `updateUser`; never stored/logged client-side. No app-side crypto (V6 n/a). |
</threat_model>
