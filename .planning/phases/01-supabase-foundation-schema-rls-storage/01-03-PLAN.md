## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| developer machine → live Supabase project | `supabase link`/`db push` use the access token + DB password; these must never enter the client bundle or git |
| browser (anon key) → live Postgres | The live database is the real trust boundary; this plan proves RLS enforces it |
| build (Vite) with live `.env.local` → bundle | Only the anon URL+key are inlined; the service-role key/DB password/access token are not `VITE_`-prefixed |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-SECRETENV | Information Disclosure | DB password / access token / service-role key in `.env.local` or a `VITE_` var | mitigate | `.env.local` carries ONLY the two `VITE_` anon vars (Task 1 acceptance); access token + DB password live in the shell env, never `VITE_`-prefixed; `.env.local` is gitignored (Plan 01); `check-no-secret.sh` confirms no `service_role` in the live build (Task 3) |
| T-03-FALSEPASS | Tampering (verification integrity) | Phase "passes" without the live push (false-positive: build/tsc green from config types) | mitigate | The [BLOCKING] `db push` (Task 2) is mandatory and verified via `supabase migration list --linked`; the skeleton read + live SQL assertions (Task 3) only pass against a truly-migrated DB |
| T-03-LIVEWRITE | Elevation of Privilege | anon client can write to the live DB | mitigate | Task 3 actively attempts an anon insert and requires it to be REJECTED; rls_assertions confirms default-deny on the real database |
| T-03-RECURSION | Denial of Service | is_admin() recurses on the live profiles table | mitigate | Task 3 calls is_admin()/reads profiles on the live DB and requires NO recursive-policy error (the SECURITY DEFINER fix from Plan 02 proven live) |
