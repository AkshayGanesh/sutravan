<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| email reset link -> SPA (hash fragment) | The recovery token arrives in the URL hash; supabase-js parses it client-side. The hash is never sent to servers/logs. |
| reset request email -> Supabase Auth | Untrusted email input; GoTrue issues + rate-limits the recovery token. |
| redirectTo target -> Supabase redirect allowlist | The redirect destination must be an exact allowlisted URL. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-3-04 | Spoofing / Tampering | reset link redirects to a non-allowlisted/attacker host | mitigate | `redirectTo` built from same `window.location.origin` + `BASE_URL`; the exact URL is on the hosted Redirect allowlist (Plan 01, D-02, Pitfall 1). |
| T-3-14 | Information Disclosure | recovery token lingers in URL/browser history after reset | mitigate | `history.replaceState` strips the token from the URL after `PASSWORD_RECOVERY` handling (Security Domain). |
| T-3-06 | Information Disclosure | reset-request response reveals whether an email is registered | mitigate | Success copy is phrased generically ("if an account exists...") — no enumeration (D-14). |
| T-3-15 | Denial of Service | reset-email rate limit (2/hr built-in) blocks legitimate retries | accept | Owner-only reset volume is far under 2/hr (D-02, Pitfall 5); the rate-limit error is mapped to friendly copy; documented as upgradeable to custom SMTP if volume grows. |
| T-3-16 | Tampering | hash-based router breaks the implicit reset flow | mitigate | Keep the path-based Wouter router + 404.html fallback; do NOT introduce a hash router (RESEARCH Pattern 4). |
| T-3-SC | Tampering | npm installs | accept | No new package installs — all deps pre-existing (RESEARCH Package Legitimacy Audit: N/A). |
</threat_model>
