<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client (anon key + user JWT) -> Postgres/PostgREST | Untrusted client input crosses here; RLS + triggers are the real enforcement. A malicious client may use the raw anon key against PostgREST, bypassing any UI guard. |
| auth.users (GoTrue) -> public.profiles | Signup-time trust boundary; the trigger runs inside the signup transaction with elevated (DEFINER) rights. |
| service-role bootstrap (no JWT) -> public.profiles | Out-of-band admin promotion; trusted local context, but the role-lock trigger still fires (Pitfall 4). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-3-01 | Elevation of Privilege | `update public.profiles set role='admin'` under a customer JWT | mitigate | `enforce_profile_role_lock` BEFORE UPDATE trigger raises when `new.role <> old.role` AND `auth.uid()` is non-null AND `not private.is_admin()` (D-04). Proven by the manual customer-JWT escalation check (VALIDATION.md / Plan 03 Task). PRIMARY THREAT of this phase. |
| T-3-02 | Tampering / Spoofing | client INSERT forging a `public.profiles` row (e.g. someone else's id, role=admin) | mitigate | No `profiles` INSERT policy exists (0002 invariant carried in the harness); rows created ONLY by the `handle_new_user` SECURITY DEFINER trigger (D-05). |
| T-3-03 | Elevation of Privilege | role injection at signup via `raw_user_meta_data.role` | mitigate | `handle_new_user` hard-codes `role='customer'`; it never reads role from metadata. |
| T-3-04 | Spoofing / Tampering | reset-link redirect to a non-allowlisted / attacker host | mitigate | Exact Redirect URLs allowlist (Site URL + the exact sub-path `/reset-password`) set in the hosted Dashboard (D-02, Pitfall 1). |
| T-3-05 | Denial of Service | trigger error aborts the signup transaction (opaque "Database error saving new user") | mitigate | Fully-qualified objects under `search_path=''` (matches 0001); the role-lock carve-out for null `auth.uid()` prevents the service-role promote from being blocked (Pitfall 4); verified on a throwaway user during the manual harness. |
| T-3-SC | Tampering | npm/pip/cargo installs | accept | No new package installs this phase — every dependency is pre-existing (RESEARCH Package Legitimacy Audit: N/A). No `[ASSUMED]`/`[SUS]`/`[SLOP]` packages. |
</threat_model>
