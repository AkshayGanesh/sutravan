<objective>
Build the auth-state layer that every frontend auth slice consumes: an `AuthProvider` context wrapping `supabase.auth.getSession()` + `onAuthStateChange` + a role fetch, exposed via a `useAuth()` hook with a resolved `loading` gate (D-12, D-13), plus an `authErrors.ts` mapper turning raw Supabase Auth error strings into friendly, non-enumerating copy (D-14). Mount `<AuthProvider>` high in `App.tsx` so the Navbar and the (later) admin guard can read session + role.

This is the frontend foundation slice — it defines the contracts (`useAuth` shape, `mapAuthError`) that the register/login/logout slice (Plan 03), the admin guard slice (Plan 04), and the reset slice (Plan 05) implement against. Interface-first: this plan ships the auth context + error mapper + provider mount, with NO routes/pages yet (those land in their own slices).

Purpose: Give the whole app a single source of truth for "who is logged in and are they an admin," with the loading gate that prevents both admin-UI flashing and wrongly bouncing a refreshing admin (RESEARCH Pitfall 2).
Output: `client/src/auth/AuthProvider.tsx`, `client/src/auth/useAuth.ts`, `client/src/lib/authErrors.ts`, and `App.tsx` mounting the provider.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client React app -> Supabase Auth (GoTrue) | Session/token handling; the client trusts supabase-js to persist + refresh the JWT (localStorage). |
| client -> public.profiles (role read) | The role is READ here for UX, but enforcement is server-side RLS — a tampered client role value cannot grant access. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-3-06 | Information Disclosure | user enumeration via differentiated auth error copy | mitigate | `mapAuthError` returns a single generic message for invalid-credentials/email-not-found (D-14, RESEARCH Security Domain). |
| T-3-07 | Elevation of Privilege | client trusts a tampered/forged `role` value from context | accept (UX-only) | The `role` in context is UX only; the real boundary is RLS `private.is_admin()` server-side (D-11). A forged client role grants no DB access. Documented design note. |
| T-3-08 | Spoofing | guard/navbar reads stale or unresolved session on refresh | mitigate | The `loading` gate stays true until session + role resolve (D-12, Pitfall 2); consumers must respect `loading` before deciding. |
| T-3-09 | Information Disclosure | session/JWT in localStorage exposed to XSS | accept | Standard supabase-js SPA posture (D-13); localStorage is the documented default. No service-role key ever reaches the client (separate guard, Plan 06). Out of scope to replace with cookie/SSR this phase (RESEARCH: do NOT pull in @supabase/ssr). |
| T-3-SC | Tampering | npm installs | accept | No new package installs — all deps pre-existing (RESEARCH Package Legitimacy Audit: N/A). |
